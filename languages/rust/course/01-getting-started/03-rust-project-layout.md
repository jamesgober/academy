# Rust Project Structure

> Learn where Rust code lives, how Cargo discovers files, and when to split a project into modules, libraries, tests, and examples.

**You will learn:**
- what `src/main.rs`, `src/lib.rs`, `tests/`, `examples/`, and `target/` do
- how binary crates and library crates differ
- how to grow from one file to a real project layout
- how examples and tests help learners and users trust your code

**Before this page, you should know:** [Create Your First Cargo Project](./02-first-cargo-project.md)

---

## The Smallest Useful Rust App

A new binary project starts here:

```text
hello-rust/
|-- Cargo.toml
|-- Cargo.lock
|-- src/
|   `-- main.rs
`-- .gitignore
```

This is enough for a tiny command-line program. Do not create extra folders just
because you have seen them in large repositories. Structure should follow need.

## The Folders You Will Actually Use

| Path | What it means | When to add it |
|---|---|---|
| `src/main.rs` | Binary crate root. Program starts here. | Created by `cargo new`. |
| `src/lib.rs` | Library crate root. Reusable code starts here. | Add when code should be tested or reused outside `main.rs`. |
| `src/<name>.rs` | Module file. Holds part of the crate. | Add when one file is doing too many jobs. |
| `src/<name>/mod.rs` | Older module folder style. | Prefer `src/<name>.rs` plus subfiles for new code unless a folder is clearer. |
| `tests/` | Integration tests. They use the public API like an outside user. | Add when you have `src/lib.rs`. |
| `examples/` | Runnable sample programs. | Add when you want to demonstrate real usage. |
| `benches/` | Benchmarks. | Later, when measuring performance matters. |
| `target/` | Build output generated by Cargo. | Never create or commit manually. |

## Binary Crate Versus Library Crate

A binary crate builds a program you run:

```text
src/main.rs
```

A library crate builds reusable code other code can call:

```text
src/lib.rs
```

Many professional Rust apps use both:

```text
inventory-cli/
|-- Cargo.toml
|-- src/
|   |-- main.rs
|   |-- lib.rs
|   |-- inventory.rs
|   `-- report.rs
|-- tests/
|   `-- inventory_flow.rs
`-- examples/
    `-- print_report.rs
```

The usual pattern is:

- `main.rs` handles command-line input, output, and process exit codes.
- `lib.rs` exposes the reusable public API.
- feature modules such as `inventory.rs` and `report.rs` hold focused logic.
- `tests/` validates behavior through the public API.
- `examples/` shows realistic usage.

## Grow a Project One Step at a Time

Start with one file:

```rust
fn main() {
    let item = "notebook";
    println!("Inventory item: {item}");
}
```

When logic becomes reusable, move it into a function:

```rust
fn format_item(name: &str, count: u32) -> String {
    format!("{name}: {count}")
}

fn main() {
    let line = format_item("notebook", 3);
    println!("{line}");
}
```

When the file grows too large or tests need access to the logic, add `src/lib.rs`:

```rust
pub fn format_item(name: &str, count: u32) -> String {
    format!("{name}: {count}")
}
```

Then call it from `src/main.rs`:

```rust
use hello_rust::format_item;

fn main() {
    let line = format_item("notebook", 3);
    println!("{line}");
}
```

Notice the crate name in code is `hello_rust`, not `hello-rust`. Rust identifiers
use underscores, so Cargo converts hyphens in package names to underscores for
the crate name.

## Add an Example Program

Create `examples/print_item.rs`:

```rust
use hello_rust::format_item;

fn main() {
    println!("{}", format_item("coffee", 2));
}
```

Run it:

```bash
cargo run --example print_item
```

Expected output:

```text
coffee: 2
```

Examples are useful because they are runnable documentation. They show how a
person is supposed to use your library from the outside.

## Add an Integration Test

Create `tests/format_item.rs`:

```rust
use hello_rust::format_item;

#[test]
fn formats_name_and_count() {
    assert_eq!(format_item("coffee", 2), "coffee: 2");
}
```

Run:

```bash
cargo test
```

Integration tests can only use public items. If the test cannot access a
function, that is a design question: should the function be public API, or
should it stay private and be tested through something public?

## What Not to Commit

Do not commit `target/`. It can become huge and it is generated by Cargo.

Your `.gitignore` should include:

```gitignore
/target
```

Commit `Cargo.toml`. Commit `Cargo.lock` for applications and course projects.

## Visual Model

```text
Cargo.toml
    |
    v
Cargo discovers targets
    |
    |-- src/main.rs  -> binary program
    |
    `-- src/lib.rs   -> reusable library
            |
            |-- tests/     -> check public API
            `-- examples/  -> demonstrate public API
```

---

## Recap

- `main.rs` is for runnable programs.
- `lib.rs` is for reusable library code.
- `tests/` checks the public API from the outside.
- `examples/` provides runnable documentation.
- `target/` is generated build output and should stay out of Git.

## Try It Yourself

Add `src/lib.rs`, move one function out of `main.rs`, create one example in
`examples/`, and create one integration test in `tests/`.
